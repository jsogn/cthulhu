# 研究笔记：性能深挖 v1（2026-08-24）

> 目标：在不降低对抗效果的前提下压缩清洗耗时。

## 1. 逐项画像（0608 30s 1080p 片段，30fps，软件编码）

| 配置 | 耗时 | 增量 |
| :--- | :--- | :--- |
| 基线（仅解码+编码） | 42.0s | — |
| +recrop 0.03 | 43.5s | +1.5s |
| +regrade | 54.3s | +12.3s |
| +denoise（原 Wiener） | 126.1s | +84.1s |
| +color_restore | 78.3s | +36.3s |
| +sharpness | 44.3s | +2.3s |
| +audio_strong | 44.1s | +2.1s |
| 平衡组合（原实现） | 186.5s | — |

结论：**去噪是最大热点**，其次是色彩还原与解码/编码底噪。

## 2. 优化与结果

### 2.1 空间降噪迁移到 FFmpeg 原生 `removegrain`

- 原来 denoise 走 uint8→float32→（scipy 滤波）→uint8 往返，内存带宽
  受限且重复分配；改为 native_filters 开启时把 `removegrain=4` 下放到
  编码器滤镜链，numpy 侧完全跳过。
- 对抗校验（通杀矩阵，全部组合口径）：SS 0.474、QIM 0.461、QIM-rep
  0.461、DWT 0.493、temporal 0.461，全部满足 BER>0.35 破坏判据；
  单看去噪，removegrain 对 SS 的 BER=0.594，优于高斯降噪的 0.000。
- 端到端：平衡组合 186.5s → **78.8s（2.4×）**。

### 2.2 高斯降噪批量向量化（非原生档位）

`attacks.spatial.gaussian` 改为整批 ndimage 调用；原生滤镜不可用的档位
（native_filters 关闭）仍走 numpy，语义不变。

### 2.3 色彩还原纯 uint8 整数域

去掉 float32 中间量，均值校准直接在 uint8 上完成。

## 3. 现状与边界

- GUI 标准/强力/全兵器预设已带 `native_filters`，自动享受 removegrain
  原生路径，无需用户操作。
- 剩余瓶颈：1080p 软件解码+编码基线约 37~42s / 30s 片段，regrade 与
  color_restore 各约十秒级，均属内存带宽型；下一步可选方向为更多原生
  滤镜下沉与 H.265 硬编路径复核。
- 回归：backend 全部 144 个测试通过。

## 4. 长视频抽样解码重构（关键帧 seek）

原 `decode_sampled` 用 `fps` 滤镜等间隔抽样，本质是**全片解码后丢弃**：
分析遍（镜头检测）与指标遍（画质/相似度）在 8 分钟素材上各自要多花
几十秒到几分钟。改为 10 个位置的关键帧 seek、每个位置只解码 cap/10 帧：

- 8 分钟 1080p 原片 cap=400 抽样：约 3.3s（旧实现需解码全片约 1~2 分钟）；
- 每个清洗任务有 3 处抽样调用（分析 400、指标 200×2），长片单任务合计
  约省 2~3 分钟；
- 抽样返回窗口起始帧号，镜头切点逐窗口检测后映射回全局帧号，避免窗口
  拼接处的假切点。

### 附带修复

逐镜头变速/切点漂移此前只在 `reorder=True` 时计算镜头边界；GUI 默认
`reorder=False`，导致这两个原语退化成一整段单镜头，效果打折。现在只要
启用逐镜头原语就会检测边界，叙事顺序仍保持不变。

## 5. 指标遍压缩与编码默认档（第三轮）

- 指标遍抽样从 200 帧降到 120 帧，对齐 VMAF 从 12 对降到 8 对；
- 抽样窗口数固定 6（短片省子进程开销、长片保留 seek 收益）；
- 编码默认档 medium → veryfast：同 crf 下 SSIM 0.9933→0.9917、
  PSNR 46.8→45.1dB，损失可忽略，编码快约 2 倍；
- 设置页与任务回退默认值同步修改（已保存的设置不变，用户可手动切换）。

回归：backend 全量测试通过、前端 typecheck 通过。

## 6. 硬编路径复核（第四轮）

30s 1080p 片段、crf/q 同口径：

| 编码 | 耗时 | 体积 | SSIM |
| :--- | :--- | :--- | :--- |
| libx264 veryfast | 2.90s | 8.4MB | 0.9917 |
| libx264 medium | 6.06s | 10.0MB | 0.9933 |
| h264_videotoolbox q70 | 4.94s | 17.4MB | 0.9939 |
| libx265 veryfast | 7.84s | 6.3MB | 0.9920 |
| libx265 medium | 12.47s | 6.9MB | 0.9928 |
| hevc_videotoolbox q70 | 5.21s | 13.7MB | 0.9933 |

结论：

- H.264 软件编码仍是速度/体积综合最优，硬件 H.264 更慢且大 2 倍，维持
  “H.264 始终软件编码”的策略；
- H.265 硬编相对软件 veryfast 仅约 1.5 倍提速、体积约大 2 倍；此前
  “约快 2 倍”文案不准确，已修正；
- 新安装默认编码加速改为「仅 CPU（软件编码）」，已保存设置不受影响。

## 7. 真实素材复核与预设瘦身（第五轮，2026-08-25）

前几轮结论多数来自合成帧；本轮用真实抖音素材（1080×1920 与 540×960
各截 15s）复核「逐原语耗时 × 判重代理风险增量」，发现两个预设原语
在真实内容上同样无收益且极贵：

| 原语 | 真实 1080p 耗时 | 代理风险增量 |
| :--- | :--- | :--- |
| DCT 重量化 step4 | +24.8s / 15s 片段 | +0.000 |
| 色度量化 128 | +3.8s / 15s 片段 | −0.002 |
| pHash 签名 ε0.035 | +13.4s / 15s 片段 | −0.038 |

处置：

- 标准/强力档移除 `dctStep` 与 `chromaLevels`（保留在「全兵器」研究档作
  未知方案对冲）；强力档同步移除多哈希联合求解、ε 0.04→0.045——联合求解
  在 1080p 约 700ms/帧，不符合非研究档的日常可用定位。
- 色彩还原维持默认开启：它是观感项（校准亮度统计），本轮不动。
- 下一步目标：签名求解器单帧 24ms 仍是变换段最大剩余热点，考虑直接一步
  校正替代 120 次迭代（需过 `fingerprint gate` 确认翻转位数不劣化）。

## 8. 威胁分级阶梯的实测锚点（2026-08-25）

用于界面“按威胁选档”的参考，不在 UI 展示具体数字（单素材代理口径，
不同素材波动大）。同一支真实 1080×1920、15s 片段（seg0608）：

| 档位 | 耗时 | 判重风险 | 备注 |
| :--- | :--- | :--- | :--- |
| 仅转码 | ~22s | 0.887 | 最弱情况锚点 |
| 低成本（裁剪 3% + 旋转 0.2°） | ~19s | 0.631 | 耗时几乎不增 |
| 标准（+签名/重量化/噪声） | ~41s | 0.600 | 哈希层打满 |
| 强力/全兵器 | 更久 | 0.56 区间 | 语义墙下收益递减 |

语义级（deep）维度任何档位均提升有限，本地武器对深度 embedding 无效。

## 9. YUV420p 快路径（2026-08-25）

长视频瓶颈实测是原始帧在 Python 侧的搬运（rgb24 6.2MB/帧往返 + 多次
拷贝），而非变换或编码本身：ffmpeg 纯转码 60s 仅 3.6s，管线“仅转码”
底噪却约 25s。默认路径（无重排/变速、静态变换已下沉原生、无 RGB 专属
选项）改为 YUV420p 紧凑平面字节往返：

- 解码/写回体积减半，省去 RGB↔YUV 转换；
- numpy 侧只剩像素重量化（平面口径）与 Y 平面签名攻击——签名攻击直接
  作用在亮度平面，与哈希层口径一致；
- 色彩还原/细节保护/伪水印等 RGB 专属选项自动回退旧路径。

实测（新标准档，真实 1080×1920）：

| 指标 | RGB 原生几何 | YUV 快路径 |
| :--- | :--- | :--- |
| 15s 片段 | 31.7s | 16.3s |
| 60s 片段 | 98s | 39.5s |
| 暗部闪烁 | 0.68 | 0.68 |
| 指纹门（phash/dhash/...） | — | 全部通过（phash +0.0278 在容差内） |

8 分钟素材外推约 13 分钟 → 5.5 分钟。

## 10. 长片分段并行（2026-08-25）

YUV 快路径上，>=80s 的素材按 CPU 核数分 2~3 段并发编码，段间用帧号
偏移保持 eq/rotate 轨迹连续，任一段失败自动回退串行；每段签名攻击线程
限制为 2，避免 3 个段互相抢核。实测（90s 真实 1080×1920，新标准档）：

| 模式 | 耗时 |
| :--- | :--- |
| 串行 | 46.8s |
| 分段 k=3（攻击线程 2/段） | 40.0s |

提速约 15%；指纹门全部通过（phash 反而更好），音画时长与暗部闪烁与
串行一致。收益低于预期的 1.5~2 倍，原因是分析/指标/音频等固定开销不随
段并行，且全机 CPU 已接近饱和；视频越长、滤镜占比越高，收益越明显。

环境变量 `CTHULHU_SEGMENT_K` 可强制指定段数（测试/调参用）。

## 11. 滤镜内部精度金字塔（2026-08-25）

滤镜链（removegrain/锐化/几何/eq）先降采样到 720p 再放大回 1080p 编码，
攻击与像素重量化保持 1080p 域（回归门最稳）。实测（90s 真实素材）：

| 方案 | 耗时 | 指纹门 | 相对 1080p 滤镜画质 |
| :--- | :--- | :--- | :--- |
| 1080p 滤镜（分段） | 40.0s | — | — |
| 720p 金字塔 | 36.5s | 全过（phash +0.0278 容差内） | PSNR 34.6dB / SSIM 0.985，轻微软化 |
| 540p 金字塔 | 34.9s | 未测 | 软化更明显，收益仅 +1.6s，不暴露 |

设置页「滤镜内部精度」默认 720（均衡），CLI 默认 1080（研究口径）。
540p 收益过低不做产品选项。至此 8 分钟素材从最初的 13 分钟压到约
3.5~3.8 分钟，剩余大头为固定开销与单线程滤镜本质成本。
