# 研究笔记：GPU / 硬件加速实测与管线性能剖面

> 2026-08-20。目标：评估 VideoToolbox 硬解/硬编码对真实素材的收益，
> 并定位端到端管线的真实瓶颈，决定「GPU 加速」的下一步方向。

## 1. 结论先行

在 Apple M4 Pro（14 核 / 48GB）上，用真实 1080×1920 素材实测：

1. **硬件解码反而更慢**：VideoToolbox 硬解输出到 CPU 内存的 raw 帧时，
   因 GPU→CPU 搬运开销，60s 1080p 耗时 2.97s，软件解码仅 1.04s（硬解 0.35x）。
2. **H.264 硬编码全面落后**：h264_videotoolbox 比 x264（medium）更慢、
   文件更大、SSIM 略低；x264 veryfast 更是 2.46s（软件最快）。
3. **H.265 硬编码是唯一收益点**：hevc_videotoolbox q70 为 6.84s，
   比 libx265 medium（13.27s）快约 2x，SSIM 略高（0.9789 vs 0.9770），
   但体积大 3.1x（17.0MB vs 5.4MB）——纯速度与体积的取舍。
4. **真正的瓶颈不在编解码，而在变换与指标**：15s 1080×1920 端到端
   剖面为「解码 1.2s + 画面变换 30~45s + 编码 7.3s + VMAF 指标 42.5s」。
5. **当前最有效的加速是 CPU 线程并行**：变换阶段按帧并行后，
   Wiener 去噪 19.1s→3.3s（5.8x）、锐化 5.7s→1.1s（5.2x）、
   重构 8.2s→1.2s（7.1x），8 线程为性价比拐点。

结论：对本架构，`-hwaccel videotoolbox` 不应接入任务管线；
H.264 输出保持 x264（可下探 veryfast）；H.265 输出可提供
「速度优先（硬编）/ 体积优先（软编）」开关；GPU 加速的优先级
应让位于「变换多线程 + 指标瘦身」，MPS/PyTorch 暂不引入。

## 2. 环境

- 机器：Apple M4 Pro，14 核，48GB，Metal 4。
- FFmpeg 8.1.2（Homebrew），可用硬编：h264_videotoolbox、hevc_videotoolbox。
- 素材：真实抖音竖屏视频（1080×1920，h264，25fps），截取 60s 与 15s 片段。

## 3. 解码矩阵（60s 1080p，灰度 raw 输出）

| 方式 | 耗时 | 备注 |
| :--- | :--- | :--- |
| 软件解码 | 1.04s | raw 灰度直出 |
| VideoToolbox 硬解 | 2.97s | GPU→CPU 搬运开销，0.35x |

## 4. 编码矩阵（60s 1080p，灰度帧源，各取最优配置）

| 编码器 | 耗时 | 体积 | SSIM（All） |
| :--- | :--- | :--- | :--- |
| x264 medium crf23 | 5.64s | 13.0MB | 0.9801 |
| x264 veryfast crf23 | 2.46s | 10.8MB | — |
| h264_videotoolbox q70 | 8.72s | 23.1MB | 0.9794 |
| h264_videotoolbox 8M | 7.63s | 58.6MB | — |
| x265 medium crf28 | 13.27s | 5.4MB | 0.9770 |
| hevc_videotoolbox q70 | 6.84s | 17.0MB | 0.9789 |

## 5. 端到端剖面（15s 1080×1920，平衡档）

| 阶段 | 耗时 | 占比 |
| :--- | :--- | :--- |
| 解码 → float64 | 1.16s | 1% |
| 画面变换（含去噪） | 30~45s | 37~51% |
| x264 medium 编码 | 7.30s | 9% |
| VMAF + aligned VMAF | 42.46s | 45% |

变换细分（15s，377 帧）：分镜重排 1.9s、变速 0.5s、重构 8.7s、
调光 4.9s、色彩还原 3.1s、锐化 6.0s、**Wiener 去噪 20.4s**。

额外发现：重排后的朴素 VMAF 恒近 0（内容时序错位导致），
对脱敏产物无参考价值；指标开销与有效性都需重构（见第 7 节）。

## 6. 变换阶段线程并行（同素材，逐帧并发）

| 操作 | 1 线程 | 4 线程 | 8 线程 | 14 线程 |
| :--- | :--- | :--- | :--- | :--- |
| Wiener 去噪 | 19.05s | 5.54s | 3.70s | 3.29s |
| USM 锐化 | 5.69s | 1.80s | 1.22s | 1.10s |
| 重新构图 | 8.15s | 2.41s | 1.44s | 1.15s |

8 线程可获 5~6x，14 线程收益递减；numpy/scipy 大块运算释放 GIL，
线程池即可，无需跨进程搬运帧数据。

## 7. 建议的落地顺序（待批准）

1. 变换阶段接入可配置线程池（默认 8），并把 `recrop/regrade/color_restore`
   等逐帧循环改为批量向量化，目标把 15s 素材变换压到 ~10s。
2. 指标瘦身：脱敏产物改用「时间对齐指标」（把处理帧匹配回最近原帧），
   朴素 VMAF 对重排内容无意义；VMAF 增加帧抽样/降采样，aligned_vmaf
   的位移估计改为抽样帧，避免全片二次解码。目标 42s → <15s。
3. 编码策略：H.264 保持 x264（veryfast 可作速度档）；H.265 提供
   「硬编速度优先 / 软编体积优先」开关，复用设置页现有 GPU 开关。
4. 不做 VideoToolbox 硬解；MPS/PyTorch 仅在多线程+向量化后仍不足
   再评估（需新增数 GB 级依赖，当前不划算）。

## 9. 落地与复测（2026-08-20）

按第 7 节落地后的实测（15s 1080×1920，平衡档含去噪）：

1. 变换阶段接入线程池（默认 8 线程）+ regrade/color_restore 批量向量化；
2. 指标重构：脱敏产物用「时间对齐 VMAF」（处理帧匹配回最近原帧后抽样评分），
   弃用对重排内容恒为 0 的朴素 VMAF；aligned_vmaf 只解码抽样帧；
3. similarity_before 改为常量（自身比较恒 1.0），相似度 embedding 抽样 60 帧；
4. H.265 硬编开关落地（设置页「编码加速（H.265）」），H.264 保持软编。

端到端结果：同配置从约 114s 降至 50.7s（约 2.2x）；其中指标部分从 42.5s
降至约 5s，变换部分从 45s 降至约 19s。剩余大头为变换与编码，可继续优化。

### 关键副作用发现：recrop 在真实素材上画质损失严重

孤立测试各变换对真实 1080p 内容的影响：

| 变换 | PSNR | SSIM | VMAF(对齐) |
| :--- | :--- | :--- | :--- |
| 仅重排 | 33.2 | 0.974 | 94.7 |
| 仅变速 0.95 | 33.1 | 0.983 | 92.6 |
| **仅重构 3%** | **17.9** | **0.826** | **7.3** |
| 仅调光 | 37.4 | 0.991 | 99.4 |
| 仅锐化+色彩+去噪 | 23.7 | 0.931 | 99.7 |

结论：**重新构图（recrop）是画质杀手**，3% 裁剪回缩就在真实素材上
造成 VMAF≈7；而 UI 平衡档文案宣称 PSNR>40dB 只在合成平滑内容上成立，
真实内容不成立。该问题为存量行为（与本次并行化无关），
属默认参数/画质口径问题，需单独决策：降低默认 recrop、改为可选开关、
或更换缩放算法，待用户确认后处理。

## 10. 决策与落地（2026-08-20）

1. **recrop 改为显式开关、默认关闭**：合规清洗面板新增「重新构图
   （裁剪回缩）」开关，文案如实标注画质损失大；默认档位不再自带裁剪。
2. **画质口径去误导**：参数表删除「典型 PSNR / 速度」这类合成基准
   宣传值，只保留基准库实测清除率；画质过差告警阈值从 38dB 调整为
   20dB（真实素材清洗后通常在 20~35dB）。
3. **内存预算自适应**：工作内存预算改为「物理内存 55%（2GB~32GB）」，
   固定 2GB 不再误拒 1080p 素材；超限时提示估算内存量。分段处理仍为
   后续长视频（>50s 1080p）的待办项。

## 11. 长视频流式化重写（2026-08-20）

固定分块自适应预算仍无法支撑十几分钟素材，按「分析遍 + 分块流式处理遍」
重写了 run_desensitize，内存与视频总长度解耦：

- 分析遍：抽样解码（fps 滤镜，约 400 帧）做镜头检测与重排置换，
  预生成逐帧调光参数；音轨整段重混后单独 mux。
- 处理遍：按重排后的输入空间分块（块大小 = 预算/8/帧字节），逐块
  解码 → float32 变换 → 写入常驻编码进程（StreamingEncoder）；变速按
  全局 floor(j*speed) 映射，与旧版一次成型口径一致。
- 指标遍：输入/输出各抽样 200 帧重解码后计算相似度、对齐 PSNR/SSIM/VMAF。
- 随机流拆分（regrade/中频/伪注入/音频各自独立种子），保证可复现。
- 关键修复：select 滤镜在本机 ffmpeg 8.1 下未按预期抽帧，改用 fps 滤镜；
  镜头差分改为逐对计算，避免整段采样帧双份临时数组。

实测（3 分钟 1080×1920 真实竖屏，平衡档含去噪/音频重混，96 帧/块）：
完整跑通，峰值内存约 16GB（旧架构同素材需 >100GB 直接 OOM），
总耗时 406s（约 0.44x 实时），进度 5%→97% 全程可见。

结论：可用性已解决；吞吐仍是下一轮优化项（块间 -ss 重定位、滤镜代偿、
更大块）。峰值内存主要由抽样帧/音频与单块变换决定，与视频总长无关。
